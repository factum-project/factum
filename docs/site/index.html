LLM 面临三个知识瓶颈

Factum 不是又一个数据库格式——它是为 LLM 设计的原生知识媒介。

读取瓶颈

LLM 接收的知识上下文以自然语言为主，缺少溯源、置信度和时间有效性。无法区分"维基百科原文"和"某 LLM 的推断"。

Factum 方案：每条知识携带七元组元数据，通过 MCP 注入上下文，规范形式比 JSON 省 66% token。

写入瓶颈

LLM 生成的结构化输出缺少语法约束，歧义解析导致不确定性，错误信息无分类，模型无法自我纠正。

Factum 方案：全括号化 S-expression 保证唯一解析树，7 类错误分类支持 LLM 自我纠正。

推理瓶颈

LLM 的"思考"在隐式权重中，没有结构化知识表示可供可审计推理。

Factum 方案：factum-l 将知识编码为连续思维向量（M3 研究项），目标语义往返 ≥ 0.95。

Factum-F 语法

全括号化 S-expression — 每个合法输入有且仅有一个解析树。
点击播放：从源码到 AST 的解析过程
( node n001 :pred ( instance-of @ACME-CORP organization ) :conf 0.99 :auth 0.95 :perm public :src ( asserted "wikidata" ) )

完整语法示例

; Acme Corp 知识图谱 ; 基础断言 — Acme 是一个组织 (node n001 :pred (instance-of @ACME-CORP organization) :conf 0.99 :auth 0.95 :perm public :src (asserted "wikidata")) ; LLM 提取 — 大股东信息（必须携带模型引用） (node n004 :pred (shareholder-major @ACME-CORP @FOUNDER-1 0.73) :conf 0.85 :auth 0.8 :perm confidential :src (extracted "doc002" [100 200] (model "gpt-4" "2024-06"))) ; 派生知识 — 子公司关系（依赖 n001，级联撤回） (node n006 :pred (subsidiary-of @ACME-SUB @ACME-CORP) :src (derived n001 "rule-subsidiary-merge") :deps [n001])

解析唯一性 — 两条保证

1. 全括号化

消除运算符优先级歧义。所有嵌套通过显式括号表达，不存在中缀表达式。

2. 命名参数顺序约束

命名参数必须在位置参数之后。消除 :keyword 前缀与符号之间的歧义。

五级溯源体系

每条知识必须声明来源。不同来源承载不同信任含义。
Level 1
Verbatim

最高信任
Level 2
Summary
人工撰写的摘要 — 人类判断
高信任
Level 3
Extracted (必须携带模型引用)
LLM 提取的知识 — 可能幻觉。强制携带 model + version
中信任
Level 4
Derived
从其他节点形式化推导 — 依赖规则正确性
取决于规则
Level 5
Asserted
人类或外部系统直接断言 — 取决于断言者
取决于断言者

MissingModelRef — 不可协商的约束

Extracted 溯源必须携带模型引用（name + version）。这在解析器中强制执行，不是文档约定。同一段文本被 GPT-4 和小模型提取的可靠性截然不同——没有模型引用的提取知识是审计链的断裂。

冲突仲裁 — 拒绝猜测

当多个节点匹配同一查询时，不确定就返回 Ambiguous，绝不猜。
LatestWins
最高权威度获胜，时间戳决胜
默认策略
HighestAuthority
严格按权威度排序
多个最高 → Ambiguous
Unanimous
仅当所有来源一致时返回
不一致 → Ambiguous

查询引擎 6 步流水线

候选生成
通过实体索引或谓词头索引获取候选节点，避免全表扫描
; 查询：ACME-CORP 的大股东是谁？ (shareholder-major @ACME-CORP ?holder ?stake) ; → 使用 by_entity["ACME-CORP"] 索引

索引级权限过滤

权限过滤在候选生成阶段进行 — 无权访问的节点永远不会被物化。

为什么后查询过滤是漏洞？

如果系统先检索所有匹配再过滤，聚合查询本身就泄露信息："返回 10 条但过滤掉 3 条" → 调用者知道存在 3 条机密节点。

权限层级（位掩码）

PUBLIC 0b0001
匿名用户可访问
INTERNAL 0b0010
内部员工可访问
CONFIDENTIAL 0b0100
分析师可访问
RESTRICTED 0b1000
仅管理员

级联撤回

源节点撤回时，所有 Derived 依赖节点自动级联撤回。软删除保留审计历史。

n001 (asserted) → cascade → n006 (derived from n001) → cascade → n007 (derived from n006)

Token 效率 — LLM 原生指标

规范 S-expression 比 JSON 省 66% token。这违反直觉——为正确性设计的形式恰好最省 token。
Token efficiency comparison: Factum canonical vs compact vs JSON

为什么规范形式比紧凑形式更省 token？

BPE 分词器将 JSON 分隔符（{ } " :）拆分为独立 token，而 S-expression 的括号和空格经常与相邻 token 合并。

JSON token 序列
{ | " | confidence | " | : | 0.85 | , | " | authority | " | : | 0.8 | }
每个分隔符 = 1 token
S-expr token 序列
(node | n001 | :pred | (instance-of | @ACME-CORP | organization) | :conf | 0.85)
括号常与相邻词合并
-66%
规范形式 token 减少（vs JSON）
-12%
紧凑形式 token 减少
-76%
紧凑形式字节减少
100%
语法往返一致性

⚠️ token 数据为启发式估算（±15%），真实分词器测量追踪于 issue #9

与其他格式的关系

Factum 不替代任何现有格式——它占据特定生态位。
格式定位Factum 的差异
RDF / JSON-LDW3C 三元组七元组，溯源/置信度/权限为一等公民。RDF 需要 reification。
CUE配置验证不同领域。Factum 验证知识声明，带时间有效性和冲突仲裁。
Datalog演绎查询Factum 支持模式匹配但增加时间有效性、置信度仲裁和溯源。
Markdown人类可读文本面向人类 vs 面向 LLM。Factum 以可读性换可验证性。
JSON通用数据交换JSON 无 schema/溯源/有效性。Factum 紧凑形式以 JSON 为传输编码。
