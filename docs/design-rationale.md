# Design Rationale

This document records the key design decisions behind Factum and the reasoning
that went into them. It is intended for contributors and reviewers who want to
understand *why* the architecture is the way it is, not just *what* it is.

## 1. Why S-Expressions?

Factum-F uses fully parenthesized S-expressions instead of JSON, YAML, or Markdown.
The reasons:

- **Parse uniqueness**: Full parenthesization eliminates operator precedence
  ambiguity. There is exactly one parse tree for any valid input. This is the
  trust foundation — if parse is non-deterministic, round-trip testing is
  meaningless.
- **LLM token efficiency (measured)**: The canonical S-expression form is
  approximately **−62% tokens** vs verbose JSON with the same metadata, while
  the compact JSON form is −53% tokens (real o200k_base measurement via
  tiktoken-rs, issue #9 resolved).
  This is counterintuitive: the compact form was designed for token economy,
  but BPE tokenizers split JSON delimiters (`{`, `}`, `"`, `:`) into individual
  tokens, while S-expression parentheses and whitespace are frequently merged
  with adjacent tokens. The form designed for correctness (canonical, fully
  parenthesized) happens to also be the most token-efficient form for LLM
  context windows — a quantitative validation of the design premise.
  This finding triggers the form-positioning decision: serve canonical to LLM
  clients, compact to storage/service-to-service paths (see ROADMAP M2).
- **Human readability is not a goal**: Factum-F is designed for LLM read/write,
  not human reading. The compact JSON form is the transport encoding; the
  canonical S-expression form is the canonical/hashing form.

## 2. Why Dec(i128, u8) Instead of f64?

Floating-point numbers introduce non-determinism across platforms (different
rounding modes, different intermediate precision). For a system whose entire
value proposition is verifiable round-trip, this is unacceptable.

`Dec(i128, u8)` stores a mantissa (i128) and a scale (u8, 0–255), representing
`mantissa × 10^(-scale)`. This gives:
- Exact decimal representation (no 0.1 + 0.2 ≠ 0.3 problem)
- Deterministic across all platforms
- Sufficient range for financial amounts (i128 supports up to ~38 digits)

**Exception**: `Confidence` and `Authority` use `f32` because they are
subjective measures that do not participate in exact arithmetic. Using `Dec`
for them would imply false precision — a confidence of 0.85 is not "exactly
85 hundredths" in any meaningful sense.

## 3. Why Index-Level Permission Filtering?

Post-query filtering (filter results after retrieving all matches) is the most
common permission vulnerability in RAG systems. The problem: aggregate queries
(count, sum, average) leak information even when individual filtered results
are correct. If a user queries "how many confidential nodes exist?" and the
system retrieves all nodes then filters, the count itself is a leak.

Factum's solution: the `by_perm` index intersects the permission bitmask at
the candidate generation stage. Nodes the query context cannot see are never
materialized. Aggregate queries operate only on the filtered candidate set.

## 4. Why Five-Level Provenance (Not Just "Source")?

A single "source" field cannot distinguish between:
- A verbatim quote from a document
- A summary generated by an LLM
- An extraction that could hallucinate
- A derivation from other nodes via rules
- A direct assertion by a human

Each level carries different trust implications. The `Extracted` level
**must** carry a model reference (name + version) because the same text
extracted by GPT-4 and a smaller model have very different reliability.
This constraint is enforced in the parser, not just in documentation.

## 5. Why SemEquiv Instead of Vector Cosine?

Semantic round-trip (encode → LLM inference → decode → check equivalence)
requires a structured comparison, not vector cosine similarity. Cosine
similarity is a continuous measure that can be gamed: two completely different
facts can have high cosine similarity if they use similar vocabulary.

`SemEquiv` uses structured comparison: exact match, entailment check, type
match, and predicate overlap. This is harder to game and produces auditable
results.

## 6. Why "Refuse to Guess" Conflict Arbitration?

When two nodes conflict (same entity, same predicate, different values) and
the arbitration policy cannot resolve definitively, Factum returns
`Ambiguous` instead of guessing. This is deliberate: a knowledge system that
silently picks one answer when it is uncertain is worse than one that admits
uncertainty. The caller can then decide whether to investigate, ask a human,
or apply a different policy.

## 7. Why Cascade Retraction (Not Hard Delete)?

When a source node is retracted, all nodes derived from it should be
invalidated. Factum uses soft delete (`NodeStatus::Retracted`) and a reverse
dependency graph (`deps_rev`) to propagate retraction. This preserves history:
"as of" queries can still see what was known at a past time, even if some
of those nodes have since been retracted.

Hard delete would break the audit chain — you could never answer "why did we
believe X on date Y?" if the upstream source was deleted.

## 8. Risk Assessment

| Module | Risk Level | Mitigation |
|--------|-----------|------------|
| factum-core (parser, types) | Low | Fuzzing, conformance vectors, depth limits |
| factum-rt (store, query) | Medium | In-memory only (RocksDB is roadmap); permission filtering tested |
| factum-mcp (bridge) | Medium | Protocol layer only; no transport layer yet; not tested with real MCP hosts |
| factum-l (latent projection) | High | Research-grade; unvalidated technical route; not started |

## 9. Implementation Status vs Design

The original design spec described a 20-week roadmap with 8 modules. The
current implementation covers the deterministic core (factum-core,
factum-rt, factum-mcp protocol/handler, factum-bench) — roughly weeks 1–12
of the plan. The research-grade module (factum-l, latent space projection)
is not started and is correctly deferred to a separate milestone.
